One feature tree, several CAD systems

2026-09-29 · punkfab/featuretree (MIT) · paper 10.5281/zenodo.23049388

A STEP file carries a part's shape but not how it was built. A native CAD file carries the history, but only its own vendor can read it. featuretree keeps a small format in between. We've now written that format up as a specification, with measurements of how well each CAD system rebuilds it.

The paper is on Zenodo. This post is the short version.

The format

A part is a JSON list of named features: sketches (with arcs), pad, pocket, fillet, revolve and placed cuts, with draft. Features refer to faces and edges by query, such as "the top face" or "the largest circle on top". They never use a CAD kernel's internal ids, so each system re-finds the geometry every time it rebuilds. A validator, ir.validate(), checks the rules every backend is allowed to assume.

{"kind": "sketch", "name": "recess_sk", "on": {"face_of": "body", "side": "top"}, "circles": [[0, 0, 6]]},
{"kind": "pocket", "name": "recess", "sketch": "recess_sk", "through": false, "length": 4}

Every system is checked the same way. The part is exported to STEP and compared with the reference build, by volume and by overlap (IoU). Each backend also records the volume after every feature, so when two backends disagree we can see which feature caused it.

Results

FreeCAD matches the reference on 10 of the 11 NIST test parts. The eleventh breaks one of the specification's rules, described below. Onshape matched every feature of our coverage parts to three decimals, apart from one pocket that removed 4.175 mm³ too much. We haven't explained that yet.

Onshape's run on the NIST parts stopped after two, when the free plan's daily API quota ran out. One of the two passed; the other built 53 of 54 features. We'll add the other nine in a revision.

What running them against each other found

No single backend reported any of these problems. Comparing backends found six:

  • The reference itself was wrong. A pad from a bottom face at z = 0 grew upward into the part. It's fixed, and none of our published results change.
  • FreeCAD kept one solid. A sketch with several separate outlines padded only one of them, halving the part.
  • Two rules the spec had never stated. Loops in one sketch must not touch. An arc with a near-zero bulge is a straight line.
  • Onshape's draft direction was opposite to our first guess. Its failure behaviour also differs: a cut that removes nothing is an error there and silently does nothing elsewhere.

Reading native files back

NIST publishes the same test parts as native SolidWorks files. We decoded each one to STEP with Onshape's importer and with an open-source decoder, and compared both with NIST's own STEP. Onshape matched on all 11. The open decoder matched on 1, and four of its wrong parts passed its own checks. One decoder is not enough. We now take geometry from the commercial importer and the feature history from the open one, and we've reported the failures upstream.

What's not new

Neutral feature exchange between CAD systems goes back to the macro-parametric work of the early 2000s, and a closely related system, CADIR, appeared in August. We don't claim to be first. What we're adding is an open spec, an MIT implementation, Onshape as a target, and measurements anyone can rerun.

Who did what
